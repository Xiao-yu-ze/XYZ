# 开发约定

## 每次写完代码必须安排团队审计

**这是硬性要求，不是建议。**

用户的明确指令："每次写完代码都要安排你的团队审计一遍才行"。

### 为什么

2 一次审计找到了 12 条真 bug，其中 2 条是"会让进程直接崩溃"的级别
（native 无锁 use-after-free、cancel 不 join 就释放复用缓冲），
还有 1 条是我上一轮自己引入的回归。

一个人写代码会在自己熟悉的错误模式里打转 —— 前面 30 条错误里有 12 条
是我自己的审计漏掉的。

### 怎么做

1. **分领域派审计员，互不通信**。至少覆盖：
   - 并发 / 协程 / 资源生命周期
   - 热路径性能与延迟
   - 坐标 / 识别正确性
   - Android 平台契约与隐藏 API

   分开派的价值在于：同一个盲区不会被所有人一起漏掉。

2. **brief 里必须写清**：
   - 只读审计，**不要改代码**
   - 项目路径、重点文件清单
   - 当前架构背景（尤其是"看起来对但实际错"的地方）
   - 输出格式：`[级别] 文件:行号 — 问题 — 触发条件 — 修法`
   - 要求区分「确定 BUG」「高度可疑」「待确认」

3. **收到报告后逐条对照代码核实，不盲信**。
   已发生过两次审计结论被推翻：
   - 「OpenCV 拒绝 mask+method=5」→ 实测断言字符串无此限制
   - 「green_mask 导致 boss 永不命中」→ 引用的模板零纯绿像素

4. **发现真问题就修，同时更新 `docs/AUDIT_LEDGER.md`**。

### 审计员的产出如何处理

- 确定 BUG → 修
- 高度可疑 → 能验证的先验证，不能验证的记进台账标「待验证」
- 待确认 → 记进台账，说明需要什么证据
- 被推翻的 → 也记进台账，写明推翻理由，避免以后重复怀疑
