## 五、MAA 语义 → 我们的节点/参数

| MAA | 我们 | 备注 |
|---|---|---|
| `next: [A, B, C]` | **等待候选**（按顺序判，第一个命中） | 顺序即优先级，和补给链一致 |
| `anchor {下一个动作: X}` + `[Anchor]下一个动作` | **控制执行(设置标识) + 跳转到标识** | 通用链靠这个回到各关自己的下一步 |
| `repeat` / `repeat_delay` | `repeatCount` / `repeatDelay` | 点波 repeat 30/70/200、delay 10~20ms |
| `pre_delay` / `post_delay` | `delay` / `pvzPostMs` | post 已有（上一轮加的） |
| `timeout: -1` | `waitTimeoutMs = 0`（无限等） | 轮询节点必须 -1 |
| `rate_limit` | 轮询间隔 | boss 识别 rl10 ≈ 每 100ms 判一次 |
| `Swipe begin/end 用锚点名` | **种植物** 节点（槽位→格子） | 锚点 `种植物_初始化_第N个槽位` / `格子C_R` 直接映射 `PvzCoords` |
| `Click 神器位置 + 葫芦小/大体型` | **使用神器** 节点（gourd_s / gourd_l） | 两步点已在执行器里 |
| `通用_无尽_识别结算` | **识别结算** 节点 | 已有（OCR 继续挑战） |
| `通用_无尽_补给识别` | **选补给** 组合动作 | 已有（上一轮封装） |
| `断网检测` | **运行多个动作**（见方案） | 两次 OCR + 点击 + 等待 |

### 坐标换算（重要）
MAA 是 **1920×1080**，我们虚拟屏 **1280×720** → **×2/3**。
例：`[1038,630,230,84]` → `[692,420,153,56]`；`Click [758,383]` → `(505,255)`；
`[1223,218]` → `(815,145)`；绿点 `[467,669,27,27]` → `[311,446,18,18]`。
（`种植物_初始化_*` 那些锚点不用换算，直接用我们自己的 `PvzCoords` 表。）

```

:轮询      等待候选 [
             候选1 开始战斗(OCR)   → 跳 :开打
             候选2 补给入口(色块)  → 跳 :补给
```

  或者做一个「开局两关」RUN_MULTI 在脚本最前面跑一次。

- `2_xinta3_过渡` 的 hub 语义 = 我们 `:轮询` 那一层，不需要单独节点。

## 七、实现时要注意的坑（已识别）

1. **`是否缺豆` 是"识别 + 动作"合一**：它既是 ColorMatch，又带 begin/end（槽1→格子1_5）。我们这边要拆成
   「颜色条件 + 种植物」两步，或给种植物加 `pvzNeedColor`（已有这个参数，可直接用）。
2. **`2_球果1` / `2_球果2` 是同一坐标点两次**：用途是点种子卡（选卡），不是点格子。需要「点击」节点（普通节点，用户已允许）。
3. **点波 repeat 200 / 70 + repeat_delay 20** 必须在同一节点内完成，不能拆成 200 个节点。
4. **第 1 关的绿点是精确色 156,223,16（lower==upper）** → 我们 `similarPercent` 要给 100 或用极窄容差。
5. **`wujin_返回`** 在 `2_3_149关` 的 next 里排第三 —— 它是"退出到选关"的分支，脚本里要不要保留待定。
6. 第 1 / 2 关的 `识别开始战斗` 后点击的是 **[758,383]**，不是开始战斗按钮本身 —— 按原样照抄，不要"修正"。

## 9.2 不能整包成顺序执行的（3 处，必须拆）

### ① `HeartTower2_3.json` 的 `2_3_149关` 是 **hub**，不是链

```json
"2_3_149关": { "action": "DoNothing", "timeout": 60000,
               "next": ["2_xinta3_识别开始战斗", "2_xinta3_识别boss关", "wujin_返回"] }
```

`next` 是**候选列表**（顺序尝试、第一个命中就执行），我们的 `运行多个动作` 是**顺序执行**，
语义完全不同。所以这一层必须做成 **等待候选** 节点：

```
:轮询   等待候选 [
           候选1 开始战斗(OCR)  → 跳 :开打
           候选2 补给入口(色块) → 跳 :补给
           候选3 继续挑战(OCR)  → 跳 :结算
        ]
```

hub 里的 `2_xinta3_过渡`（timeout -1，next 同样是这三项）**等价于 `:轮询` 本身**，不用单独建节点。

### ② `CheckNetwork.json` 是**中断式检查**，不是流程的一步

它被挂在别的节点的 `next` 里当候选：

```json
"2_xinta3_点波": { "next": ["通用_无尽_识别结算", "断网检测", "2_xinta3_喂豆香蕉1"] }
```

也就是说它是"每一轮顺带看一眼有没有断网"。做成独立的 `运行多个动作` 放在流程中间，
语义就变成"必须先检查"，节奏完全不同。正确做法是把它作为**候选**塞进对应的等待候选里
（可以和结算共用一轮判断）。

### ③ 各处的 `通用_无尽_识别结算` 同理

它出现在几乎所有 `next` 列表里 —— 是"每轮都看一眼是不是已经结算了"，属于候选，不是步骤。
我们已有「识别结算」游戏节点，直接作为候选。

## 9.3 建议直接**不做**的两个文件

| 文件 | 为什么不做 |
|---|---|
| `HeartTower0_0.json`（心塔阵容选择） | 内容只有 `"next": []`，是空占位 |
| `HeartTower2_0.json`（Entry2 → 种植物_初始化_植物位置） | **初始化链是给 MAA 的锚点体系用的**：它要把 `槽位1..8`、`能量豆`、`铲子`、`格子1_1..9_5`、`神器位置` 一个个命名成锚点，后面的 Swipe 才能按名字引用。我们的坐标表（`PvzCoords`）本来就内置这些点位，脚本里直接写 `种植物 卡槽3 → 第1行第5列` 即可 —— **没有初始化这回事** |

## 9.4 最终脚本骨架

```
:轮询    等待候选 [开始战斗 → :开打 ; 补给入口 → :补给 ; 继续挑战 → :结算]
:开打    运行多个动作[ 心塔·第1关 ]        ← 第 1 关阶段
         运行多个动作[ 心塔·第2关 ]        ← 第 2 关阶段
         （之后进入循环）
:循环    等待候选 [开始战斗 → :打第3关起 ; 补给入口 → :补给 ; 继续挑战 → :结算]
:打第3关起  运行多个动作[ 心塔·第3关起·关内 ]  → 跳 :循环
:补给    选补给 → 跳 :轮询
:结算    识别结算(点继续挑战) → 关卡+1 → 跳 :轮询
```

第 1、2 关是"开局固定两关"，所以放在循环之前跑一次；第 3 关起才进循环。
